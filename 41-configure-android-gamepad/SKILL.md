# 41 配置安卓手柄

作者：李逊 · 公开版 v1.0.1 · MIT License

目标是在用户指定的安卓机器上保留无线连接，完成可独立启动的手柄配置；掌机自带按键和现有稳定方案继续可用。先选下面两部分之一，共用全局模拟器配置与验收流程。

| 部分 | 适用情况 | 权限与入口 |
|---|---|---|
| 一、不需要内置手柄兼容 | 游戏接受 Android 外接手柄；只需连接、补映射或把 USB 报告桥接为虚拟手柄 | 优先普通 App 和系统原有 USB/uinput 能力；普通权限是否可用要在本机验证 |
| 二、需要内置手柄兼容 | 普通模式有系统输入，但目标游戏只响应掌机自带手柄 | **由用户提供该机器的 root 入口并授权用途**，验证后适配；RP6 的厂商入口不能推定其他设备也有 |

## 共用准备

1. 复用本次已经提供的信息和授权，核对目标型号、系统版本、序列号、手柄型号、连接方式与接收器 VID/PID。ADB 多设备时每条设备命令指定 `-s`；无线配对端口与连接端口分别回读，不能凭配对成功认定已连接。只操作指定设备。
2. 记录现有可用版本、签名、模式、模拟器全局配置和必要的存档备份。只在副本上开发；保留稳定 APK、源代码与恢复路径。先安全保存/退出游戏，再停止模拟器、改配置或重启。
3. 分清故障层次：USB 枚举 → 原始报告 → Android 手柄事件 → 模拟器玩家/映射 → 游戏实际响应。扩展坞鼠标可用仅说明部分 USB 链路正常；不要据此认定接收器已识别。已有系统输入时先配置游戏/模拟器，不必重写桥接。
4. 设备操作优先 ADB、配置、UI XML 和日志；图形与输入验收使用实际画面及用户实测。截图保留原件，文字优先用 UI XML/日志；图形判断使用清晰整图及必要的原生分辨率局部。接收器模式的官方切换方法以准确型号说明书为准，不编造组合键。

## 第一部分：不需要内置手柄兼容——配置安卓手柄

### 先验证最小链路

- 保留用户选择的 2.4G 接收器，不擅自换成蓝牙或电脑中转。核对 USB 接口、端点与权限；需要 USB 授权时让用户在设备确认。
- 若系统已有 gamepad/joystick 事件，直接进入全局配置。若只有 USB 报告，先用普通 App 读取并展示原始按钮和轴数据，再验证普通 App UID 能否创建虚拟手柄。ADB shell 成功不证明普通 App 成功。
- 只有本机原有能力确实允许时才使用 `/system/bin/uinput` 等路径。普通权限不可用时，报告具体缺失能力；不能把一次成功泛化为所有安卓无需 root，也不能自行提权。
- RP6 指定 USB 接收器 的协议、普通模式和已验收材料见 [已验证适配](references/rp6-usb-bridge.md)。其他型号先采样并建立映射，不能直接套用其 VID/PID、报告格式或键轴范围。

### 做成独立 App

- 原始接收器 → 报告解析 → Android 虚拟手柄；USB 读取和输出不依赖电脑、ADB 会话或工作站服务。提供“启动/停止”、明确状态、模式持久化和必要的前台运行通知。
- 验证 ABXY、十字键、LB/RB、Select/Start、L3/R3、双摇杆正负全范围、双扳机从零到满量程及释放。USB 安静等待不等于断线；超时继续等，真正断开或停止时释放请求、连接、虚拟设备及震动。
- 背键是否可独立映射取决于报告：单独采样 M1/M2 并用普通按键作对照。没有独立数据时说明限制，不凭空生成 M1/M2。按用户接受的组合键提供菜单/返回；触发后抑制该组合本身，松开再解锁。
- 震动分三层验收：USB OUT 短震、Android 手柄振动 API、游戏实际震动；分别记录。只有状态回调时不能承诺精确强度和时长，停止/断开须发停震。

## 第二部分：需要内置手柄兼容——配置安卓手柄

### 确认需要兼容及用户提供的 root 入口

1. 普通桥接系统回读正常后，先让目标游戏在桥接运行时重新启动，比较外接和内置手柄。只认内置的现象才进入本路径；模拟器没绑定不等于需要 root。
2. **机器的 root 入口由用户提供**，例如厂商“以 root 身份运行脚本”、已有授权服务或已有 `su`。沿用会话中已提供并授权的入口，不重复询问。缺失时仅询问入口/执行方式，同时完成不依赖它的普通模式和备份工作。技能调用本身不授权寻找漏洞、安装 root、解锁、刷机或关闭 SELinux。
3. 通过该入口先执行最小诊断，回读 `id`、执行上下文、目标输入节点元数据。页面写着“root”不证明实际身份；电脑 shell 的 root 不证明 App 能调用；一次执行成功不证明重启后仍可用。
4. 区分“用户手动运行脚本”和“App 可调用该入口”。按实际能力决定 App 一键启动或设备端脚本启动。需要额外工具/每次重启额外步骤时先说清变化，不把它称为已实现一键。

### 最小授权、独立运行与恢复

- 先识别真实内置控制器：名称、VID/PID/version、键轴能力、范围、节点类型及所有者；动态查找 `eventN`，不能硬编码上次编号。重复匹配、身份变化或范围不明时停止兼容路径，保留普通模式。
- 选用适合该设备的最小授权/特权辅助方式。RP6 已验证方法是厂商服务临时将**唯一目标节点**的所有者交给 App，保留原组和权限，退出时收回；其他设备要重新设计并验证，不批量修改 `/dev/input`，不用全局 `chmod 666` 或公开任意 root 命令接口。
- 通过既有内置输入设备提交与其能力一致的事件，避免再建第二个虚拟手柄干扰目标游戏。键轴映射和二进制事件布局以当前设备/进程 ABI 为准。App 停止、异常和模式切换时释放自己产生的按键/轴、关闭句柄并恢复授权；处理上次进程退出遗留的授权。
- 配置运行前后回读权限/身份及事件。权限被拒绝时停止该权限范围内的操作，保留可用普通路径；只有用户补齐授权或设备权限状态发生变化后才重新验证。
- 特别区分“没有额外安装 root”和“完全不使用 root 权限”。RP6 的成功版本使用用户授权的既有厂商 root 服务，不能宣传为纯普通权限兼容。

## 两部分共用：模拟器全局配置

配置常用模拟器时读取 [全局映射与快捷键](references/emulators.md)。在全局玩家配置中**追加**外接手柄，保留内置绑定、传感器和未授权修改的设置；不以某一个游戏的 override 代替全局设置，也不直接用外接 profile 覆盖内置 profile。配置语法可能把重复键、OR、组合键区别处理，先验证一项再批量应用。

退出模拟器后写入，重开读取保存结果，再用两套实体控制验证。没有游戏可测试的模拟器标记“已配置/回读，未游戏实测”，不能宣称全通过。

## 完成标准

- 当前设备：USB 报告、系统输入和目标游戏按键/轴都通过；全局映射覆盖本次约定的模拟器，内置按键仍可用。
- 冷启动：安全保存后重启；用户不先开无线调试/电脑桥接，直接在掌机打开 App 并启动，再测游戏。测试窗口内电脑不启动桥接或发送游戏输入。若方案依赖用户提供的设备端脚本，按实际步骤单独验收并说明。
- 兼容路径额外回读授权获取/释放、重启后恢复，保留普通路径及稳定版本。不能用重启前偶然可写的节点证明可长期独立运行。
- 在任务目录留型号/序列号、APK 版本/签名或校验、模式、授权入口及范围、配置与备份、实际通过项、待验项和恢复步骤。回复只声明已有证据的结果；用户在测试时不抢占设备。
